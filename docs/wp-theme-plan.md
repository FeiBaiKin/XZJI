# XZJI 技术方案（WordPress 主题方向）

> 状态：方向已定（2026-10-05），首版范围已定，插件选型待实机验证
> 取代：[docs/archive/phase1-tech-plan.md](archive/phase1-tech-plan.md)（v1 自研 Go + Nuxt 方案，已封存）

## 1. 方向变更

### 1.1 为什么掉头

v1 是一套完全自研的程序：Go 后端 + Nuxt 4 前台 + Vue 3 后台，M0–M6 六个里程碑全部完成，2026-10-05 上线 www.xzji.cc。实机跑下来，结论是不划算：

- **开发量太大**：约 3.8 万行代码、16 个提交。其中很大一部分是在重造 WordPress 早就有的东西——用户体系、会话与 CSRF、评论、媒体库与图片多尺寸、回收站、SEO、页面缓存、后台管理。
- **没有生态兜底**：自研的东西出问题只能自己修。编辑器、图片处理、支付渠道每加一个都是一次新开发，而不是装一个插件。
- **运维复杂**：上线要同时养 OpenResty + MariaDB + Go 运行环境 + Node 运行环境四个容器，外加一套自建的数据库迁移和前后台缓存清除机制。

### 1.2 新方向的两条硬原则

1. **能交给 WordPress 的，一律不自研。** WP 核心有的（用户、评论、媒体、分类法、回收站、区块编辑器、REST API、后台）直接用；成熟插件有的（SEO、缓存、SMTP、备份、安全、图片优化）装插件。
2. **主题只做两件事**：本站的外观，以及 WP 生态里确实没有、又不值得为它装一整套插件的最小业务胶水。

判断一个新需求该谁做，按这个顺序问：WP 核心有没有 → 成熟插件有没有 → 主题写最小实现。

### 1.3 v1 怎么处理

| 对象 | 处理 |
|---|---|
| v1 代码 | 封存在 `archive/v1` 分支和 `v1.0-standalone` 标签，历史提交完整保留，随时可回退 |
| main 上的 v1 目录 | 暂时保留作只读参考（页面结构是主题开发时的对照物），不再构建、不再维护 |
| 线上 www.xzji.cc | 继续跑 v1，等 WP 站验证通过再一次性切换 |
| v1 文档 | 移入 `docs/archive/`，顶部标注历史 |

## 2. 定位与首版范围

站点定位不变：垂直资源站，1000 ~ 1 万篇内容。

**首版（M1）只做三件事：内容、下载、支付。**

| 方向 | 明细 |
|---|---|
| 内容 | 分类、标签、平台；文章与资源发布；资源扩展信息（版本、文件大小、更新日志、截图、自定义属性）；封面图与软件图标 |
| 下载 | 每篇资源可挂多个下载地址（网盘名、链接、提取码、解压密码）；下载地址按条件可见 |
| 支付 | 单篇购买 → 生成订单 → 彩虹易支付 → 回调验签 → 解锁下载地址 |

**首版不做**，留到后续里程碑：会员等级与套餐、升级按剩余价值折算、余额钱包与流水、评论可见解锁、链接失效反馈、优惠券与卡密、每日下载次数限流。

**WP 原生白拿**，首版零开发：用户注册登录与找回密码、评论与审核、媒体库与多尺寸缩略图、回收站、草稿与定时发布、置顶、搜索、后台管理、REST API。

## 3. 技术选型

| 用途 | 选择 | 理由 |
|---|---|---|
| CMS | WordPress 最新稳定版 | 业务能力的主要来源 |
| 语言 | PHP 8.2+ | 由 1Panel 的 PHP 运行环境提供 |
| 数据库 | MariaDB | 沿用服务器上现有实例，另建独立库 |
| 主题形态 | **经典主题（PHP 模板）**，不用区块主题（FSE） | 见 3.1 |
| 样式 | 直接复用 `design/xzji.css` | 698 行设计变量与组件样式，纯 CSS，见 6.4 |
| 构建工具 | **不引入** | 主题只有 PHP + 原生 CSS/JS，改完即生效，不需要 Node 工具链 |
| 内容编辑 | Gutenberg 区块编辑器 | 不自研编辑器，v1 的 TipTap 废弃 |
| 自定义字段 | ACF | 资源扩展信息 |
| 部署 | 1Panel 网站（PHP 运行环境） | 见第 8 节 |

### 3.1 为什么用经典主题而不是区块主题

- `design/` 下是现成的 HTML + CSS，翻译成 PHP 模板的还原度最高；拆成区块模板反而难控。
- 国内主题与插件生态（`the_content` 过滤、短代码、模板层级、`single-{type}.php`）基本都按经典主题设计，区块主题兼容性差。
- 不需要构建步骤，`functions.php` 里 `wp_enqueue_style` 挂上 CSS 就行。

## 5. 内容模型

### 5.1 内容类型与分类法

| 名称 | 类型 | 说明 |
|---|---|---|
| `post` | 内置文章类型 | 教程、资讯类内容 |
| `resource` | 自定义文章类型 | 资源，公开可查询（`public`、`has_archive`），归档页与后台菜单自动分开 |
| `category` | 内置分类法 | 文章与资源共用一棵分类树，最多两级（靠编辑约定控制，不做强制校验） |
| `post_tag` | 内置标签 | 文章与资源共用 |
| `platform` | 自定义分类法 | 仅挂 `resource`，如 安卓 / Windows / macOS / 源码 / 主题 |

不用「统一 `post` + 一个字段区分类型」：WP 里自定义文章类型更自然，模板层级（`single-resource.php`）、归档、后台列表、查询都自动分开，不必到处加 meta 条件。

### 5.2 资源的字段（ACF 字段组）

| 字段 | 类型 | 说明 |
|---|---|---|
| 平台 | `platform` 分类法 | 与分类法绑定，不另存字段 |
| 版本 | 文本 | |
| 文件大小 | 文本 | 形如 `1.2 GB` |
| 软件图标 | 图片 | 没有封面图时，前台按图标主色配底色显示 |
| 自定义属性 | 可重复（名称 + 值） | 语言、官网、系统要求等，前台以表格展示 |
| 更新日志 | 可重复（版本 + 日期 + 说明） | 新的在前，前台以时间线展示 |
| 下载地址 | 可重复（名称、链接、提取码、解压密码） | 见 5.3 |
| 价格 | 数字（单位：分） | 0 表示不单卖 |

字段组用 PHP 代码注册（`acf_add_local_field_group`），不从后台导出 JSON——这样字段定义进版本库，换环境不会丢。

### 5.3 付费与隐藏内容

v1 有一套自研的「隐藏块 + 解锁条件」。WP 上不自研解析器，用短代码：

| 短代码 | 可见条件 |
|---|---|
| `[xzji_hide]…[/xzji_hide]` | 登录后可见 |
| `[xzji_paid]…[/xzji_paid]` | 已购买本篇后可见 |

**硬约束（从 v1 继承，不可放宽）**：

- 受保护的内容**绝不能出现在未解锁访客的 HTML 里**。短代码在 `the_content` 过滤里服务端求值，无权时只输出占位符和购买按钮，不输出内容本身。
- 不允许用 CSS 或 JS 隐藏来实现付费墙——那是能被 F12 直接看穿的。
- 因此**页面缓存必须按登录态区分**：缓存插件要配成登录用户不命中页面缓存，否则已购买用户会拿到未解锁的那份 HTML。这是首版配置里最容易踩的坑。

### 5.4 下载计数

主题在输出下载链接时记一次数（存资源文章的 meta）。首版不做每日次数限制——那是给「会员免费下载」用的规则，会员首版不做。

## 7. 支付

首版必须落地「单篇购买 → 支付 → 解锁」。这是 WP 核心没有的部分，也是首版唯一可能写业务代码的地方。

### 7.1 接入方式：先插件，后自研

现成的易支付网关在 `epay.xzji.cc`（彩虹易支付）。协议是标准的：`submit.php` 页面跳转 / `mapi.php` API 下单，MD5 签名（参数按字典序拼接 + KEY 后取 md5），异步回调 `notify_url` 验签，`api.php` 查单。

按 1.2 的原则，顺序是：

1. **先试装现成插件**。WP 上有多款「付费下载 + 易支付」一站式插件（候选：Erphpdown 及各类易支付网关插件）。先实际装一个走通全流程。**如果一款插件同时解决了下载管理、支付、解锁三件事，主题就只管外观，首版工作量再降一档**——这是最优先要验证的路径。
2. **插件覆盖不了再自研最小通道**。主题内 `inc/payment/epay.php`，只做下单、回调验签、查单三件事，订单落在自定义文章类型 `xzji_order` 上（或自建表）。

### 7.2 订单与解锁规则

无论走插件还是自研，对用户可见的行为要一致：

| 事项 | 规则 |
|---|---|
| 订单过期 | 30 分钟，过期未付自动关闭 |
| 支付方式 | 首版只接彩虹易支付，微信/支付宝由易支付侧选择 |
| 回调幂等 | 按订单号 + 已支付状态判断；重复回调直接返回成功，不重复发放 |
| 金额单位 | 一律用「分」存储，展示时格式化 |
| 解锁判定 | 存在该用户对该资源的已支付订单才算解锁；**服务端判断**，未购买者的 HTML 里没有下载地址 |
| 退款 | 首版不做线上退款，后台人工处理 |
| 补单 | 以易支付 `api.php` 查单为准，后台提供手动同步入口 |

## 8. 部署

沿用现有 1Panel 服务器（117.55.232.75），WP 站与 v1 站并存，验证通过后再切换。

| 项 | 做法 |
|---|---|
| 运行环境 | 1Panel「网站 → 运行环境 → PHP」，PHP 8.2+ |
| 站点 | 1Panel「网站 → 网站」新建 PHP 站点，域名 `www.xzji.cc`，证书沿用现有 Let's Encrypt |
| 数据库 | 新建独立库（如 `xzji_wp`），**不与 v1 的 `www_xzji_cc` 混用**，便于随时切回 |
| 主题 | `theme/xzji/` 打包上传，或整目录软链到 `wp-content/themes/xzji` |
| 对象缓存 | Redis（1Panel 应用商店），配 Redis Object Cache 插件 |
| 页面缓存 | 缓存插件；**必须配成登录用户不命中页面缓存**（见 5.3） |
| 上传目录 | `/wp-content/uploads`，由 OpenResty 直出 |
| 定时任务 | 1Panel 计划任务：每日备份数据库与站点目录、WP 定时任务 |
| 切换 | 两站并存，验证通过后切域名绑定；v1 停用但保留一段时间再清理 |

**v1 踩过的坑，部署时留意**：

- 1Panel 运行环境的「端口外部访问」**默认开启**，必须手动关掉，否则端口直接暴露公网、绕过 Nginx。PHP 运行环境同样要检查。
- 上传目录必须在 OpenResty 容器挂载的 `/wwwroot` 之内，否则 Nginx 直出不了。

## 10. 目标与验收

### 10.1 性能目标

v1 的指标是在自研渲染链路上测的，不能直接沿用。WP 方向重新定：

| 指标 | 目标 | 说明 |
|---|---|---|
| Lighthouse 移动端性能 | ≥ 80 | 达不到先查主题里多余的脚本与样式 |
| 命中页面缓存的首页响应 | < 50ms | 由缓存插件 + Nginx 提供 |
| 首屏 JS（gzip 后） | < 120KB | 主题自身脚本控制在 20KB 内，其余是 WP 与插件基线 |
| 服务器配置 | 沿用现有 7 核 3.8G | 无需升级 |
| 插件数量 | 首版尽量少 | 每多一个插件就是一份长期维护成本 |

### 10.2 视觉还原

硬要求：主题的每个页面与 `design/` 对应页面逐页比对。配色、圆角、阴影、渐变、间距以 `design/xzji.css` 的 CSS 变量为准，不凭感觉调。

### 10.3 安全与内容保护

- 受保护内容不出现在未解锁访客的 HTML 里（见 5.3），这条要在验收时**查看网页源代码确认**，不能只看页面表现。
- 支付回调必须验签；订单状态更新要带原状态条件，保证重复回调幂等。
- 后台用强密码 + 登录失败限制（插件）。
